Speaker 3: Manthan Vinod Dhamal
Roll No. 35 • Relational Theory & Normalization Lead
⏱️ 4:00 – 6:00 (2 Mins)
🗣️ What to Say (Spoken Dialogue):
"Thank you, Takshak. Respected Sir, in database engineering, poor design leads to Insertion, Update, and Deletion anomalies. My focus was mathematically proving that our schema satisfies Third Normal Form (3NF) and Boyce-Codd Normal Form (BCNF).

• 1NF (Atomic Attributes): We eliminated all repeating groups and comma-separated tags. Every column holds indivisible values, and every table has a defined primary key.
• 2NF (No Partial Dependencies): A table in 1NF is in 2NF if all non-prime attributes are fully functionally dependent on the entire primary key. In assignments, technician details are not stored directly; they reference user_id, eliminating partial key dependencies.
• 3NF (No Transitive Dependencies): 3NF mandates that no non-prime attribute depends transitively on a primary key (X → Y → Z). Initially, complaint_id → category_id → dept_name. If department names changed, update anomalies would occur across complaints. We decomposed this into independent tables: departments, categories, and complaints.
• BCNF (Strict Superkeys): In the feedback table, both feedback_id and complaint_id act as candidate keys, satisfying BCNF with zero redundancy."

"Thank you, Ali. Respected Sir, to guarantee that business logic is enforced at the database layer, we engineered Automated Database Triggers and managed ACID Transactions.

We implemented 3 essential triggers in our MySQL DDL:
1. trg_after_complaint_assigned: An AFTER INSERT trigger on assignments. As soon as an admin dispatches a technician, the trigger automatically flips complaint status from 'Pending' to 'Assigned' and links assigned_to.
2. trg_auto_close_on_feedback: An AFTER INSERT trigger on feedback that auto-transitions the ticket to 'Closed' and stamps closed_at = NOW().
3. trg_audit_status_update: An AFTER UPDATE trigger on complaints logging all status transitions into activity_logs.

ACID Guarantees: Operations execute inside atomic transactions (BEGIN TRANSACTION ... COMMIT). If any table insertion fails, changes rollback immediately, ensuring Consistency and Isolation.

To conclude: Campus Fix successfully demonstrates relational modeling, normal forms, triggers, and transactions in a real-world institutional platform. We are now ready for viva questions."

🎯 Academic Viva Voce Defense Sheet (Questions & Model Answers)
Q1: "Why is the complaints table in 3NF and not just 2NF?" Answered by: Manthan (Roll 35)
Model Answer: "Sir, in 2NF, transitive dependencies can still exist. In our domain, department_name depends on category_id, which depends on complaint_id. If we kept dept_name inside complaints, any department update would require updating hundreds of complaint records. Decomposing it into departments and categories removes transitive dependencies and satisfies 3NF."
Q2: "What happens if an admin tries to delete a department? Will tickets be lost?" Answered by: Takshak (Roll 30)
Model Answer: "Sir, we have set ON DELETE RESTRICT on the categories → departments foreign key. The database rejects the deletion of a department if active categories or complaints reference it. On users.department_id, we set ON DELETE SET NULL so staff accounts are preserved."
Q3: "Why did you use database triggers instead of handling status updates in frontend JavaScript?" Answered by: Rohit (Roll 53)
Model Answer: "Sir, frontend validation can be bypassed or disabled. Database triggers execute directly in the RDBMS engine. Whether a record is inserted through our web UI, a mobile client, or direct SQL script in MySQL Workbench, the trigger guarantees that status transitions and audit logs are recorded 100% consistently."
Q4: "Can you explain the difference between WHERE and HAVING in your SQL queries?" Answered by: Ali Asgar (Roll 40)
Model Answer: "Sir, the WHERE clause filters individual records before aggregation. HAVING filters group-level results after GROUP BY. For example, to filter complaints lodged in 2026, we use WHERE YEAR(created_at) = 2026. To find departments with more than 5 complaints, we use GROUP BY dept_name HAVING COUNT(*) > 5."
Q5: "How is the 1:1 relationship between complaints and feedback enforced?" Answered by: Takshak / Sarth
Model Answer: "Sir, each complaint should have at most one feedback review. We enforce this at the schema level by placing a UNIQUE constraint on feedback.complaint_id in addition to its Foreign Key. Any attempt to insert a second review for the same ticket triggers a duplicate key error."
